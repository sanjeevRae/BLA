# BLA — New Database Schema Design (Prisma / PostgreSQL)

**Status:** design for the Next.js rebuild · **Date:** 2026-11-15
**Inputs:** master spec Parts 6, 7, 13, 20; Phase 0 database audit (`~/workspace/BLA-audit/database-audit.md`).
**Target:** the existing Supabase PostgreSQL database, new tables provisioned by Prisma migrations in a dedicated `app` schema (see §13 — the legacy `public` schema is left untouched until cut-over is verified).

---

## 0. Global conventions (apply to every entity unless stated otherwise)

| Topic | Decision |
|---|---|
| Primary keys | `id String @id @default(uuid())` → PostgreSQL `uuid`. UUIDs keep continuity with the legacy system (whose `users.id` mirrored Supabase Auth UUIDs) and let tracking/reference IDs be generated anywhere without sequences. |
| Business references | Human-facing numbers are separate unique columns, never the PK: `orderNumber` (`ORD-1001`), `shipmentNumber` (`SHP-1001`), `Package.trackingId`, `transferNumber`, `tripNumber`, `invoiceNumber`, `LedgerTransaction.reference`, `incidentNumber`. Generated by the application service inside the creating transaction. |
| Timestamps | `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`, stored as `timestamptz` in **UTC**. All display converts to **Asia/Kathmandu** in the application layer (spec Part 18). Event tables additionally separate *event time* (`occurredAt`, when it physically happened) from *recorded time* (`createdAt`, when the server wrote it) — required by spec §7.4 and offline-sync (Scenario 10). |
| Money | **Integer paisa in `BigInt`** (1 NPR = 100 paisa), column `currency String @default("NPR")` where relevant. Chosen over `Decimal` because: ledger sums must be exact (spec §13.5) and integer arithmetic can never accumulate rounding drift; `numeric`→JS conversions at the Prisma boundary invite float error precisely where finance code can least afford it; and per-row amounts are unbounded enough (vendor settlement aggregates) that 32-bit `Int` paisa (~Rs 2.1 crore ceiling) is unsafe, hence `BigInt`. The API layer serialises `BigInt` as a string. No `Float` money anywhere — the legacy schema's `numeric(12,2)` + `currency default 'INR'` (audit §1.3, R10) is not carried over. |
| Weights / dimensions | `Decimal @db.Decimal(10,3)` kg and `Decimal @db.Decimal(10,2)` cm. Weight is measurement, not money, so decimal is correct here; declared / actual / volumetric / billable are separate columns (spec §6.3, missing in the legacy schema per audit §5). |
| Status representation | Lifecycle and status fields are **`String` columns constrained by database CHECK constraints**, with the allowed values centralised in one TypeScript domain module and transitions enforced by services — *not* PostgreSQL enums. The legacy project hit enum rigidity directly (audit R7: error 55P04, no same-transaction use of new enum values), and spec §4.1 requires status rules to be configurable. Prisma enums were rejected for the same reason. |
| Soft delete / archival | Entities with history or financial significance are **never hard-deleted**. They carry a lifecycle status (`ACTIVE / INACTIVE / SUSPENDED / ARCHIVED` etc.) and, where a delete-like action is genuinely needed, `archivedAt DateTime?` + `archivedById`. This replaces the legacy design where `ON DELETE CASCADE` chains could wipe an order's items, packages, payments and entire status history in one statement (audit R5). |
| FK delete behaviour | **Explicit `onDelete` on every relation. Default: `Restrict`.** No `Cascade` on any history-bearing, financial, custody, event or ledger relation — a referenced row simply cannot be deleted while history points at it (and in practice such rows are archived, not deleted). `SetNull` is used only for optional attribution on non-history tables (e.g. `Vehicle.assignedDriverId`). `Cascade` is permitted **only** inside pure composition/config aggregates whose children have no independent history: `OrderItem→Order`, `PackageItem→Package`, `DeliveryInstruction→Order`, `WarehouseOperatingHours→Warehouse`, `RolePermission→Role/Permission`, `UserRole→User/Role`, `DriverCapability→Driver`, `TransferItem→Transfer` *while the transfer is still DRAFT* (enforced in the service; the FK itself is `Restrict` once dispatched — see §7). |
| Optimistic concurrency | Mutable operational aggregates (`Package`, `Transfer`, `Trip`, `DeliveryAssignment`, `CODCollection`) carry `version Int @default(1)`, incremented on every service mutation and checked on update (spec §20.1, Scenario 8 — two staff acting on the same package). |
| Idempotency | Every externally retryable mutation accepts an idempotency key; the tables that originate such mutations store it in a **unique** column (`TrackingEvent.idempotencyKey`, `TransferScan.idempotencyKey`, `Payment.idempotencyKey`, `LedgerTransaction.idempotencyKey`). A retry returns the original row instead of duplicating the effect (spec Scenarios 7 and 12; audit R8 — the legacy schema had none of these). |
| Append-only tables | `TrackingEvent`, `InventoryMovement`, `PackageCustody` (rows are closed, never edited), `CustodyHandover`, `LedgerTransaction`, `AuditLog`, `TransferScan`, `DeliveryAttempt`, `StockMovement`. Append-only is enforced three ways: the application exposes no update/delete path; Prisma models omit `updatedAt`; and the migration adds a `BEFORE UPDATE OR DELETE` trigger that raises, so even direct SQL cannot rewrite history. |
| Warehouse scoping | Every warehouse-owned row carries an explicit `warehouseId` (or reaches one through a mandatory FK chain), and every scoped query filters on the caller's `WarehouseMembership` set in the data-access layer (spec §20.2). A warehouse ID from the client is never trusted as proof of access. PostgreSQL RLS may be layered on later as defence-in-depth; it is not the primary mechanism (the legacy failure mode — service-role bypass making RLS decorative, audit R2/R4 — must not be repeated). |

## 1. Identity & access

### User
The single login identity for every human in the system (staff, riders, vendor users, customers with accounts). Replaces legacy `public.users` **and** retires Supabase Auth as the credential store — the new stack owns credentials via Auth.js (spec §21.1: established library, no hand-rolled crypto). Legacy password hashes live in `auth.users`, which is not exportable, so migrated users receive a `UserInvitation`/password-reset flow to set a new password (see §13).
- `email String` — normalised lowercase on write; `@@unique` (add a `citext` column type in migration SQL if case-insensitive matching at the DB level is preferred).
- `passwordHash String?` — Argon2id/bcrypt hash from the auth library; `null` until an invited user sets a password. Never a raw password, never exposed to the client.
- `fullName String`, `phone String?` (indexed — login-adjacent lookups and rider contact), `avatarFileId String? → FileAsset (Restrict)`.
- `status String` CHECK in (`ACTIVE`, `SUSPENDED`, `DEACTIVATED`) default `ACTIVE`. Suspension must revoke sessions (§10/Scenario 17): the auth layer checks `status` on every session read, and suspension deletes/expires `Session` rows.
- `emailVerifiedAt DateTime?`, `mustChangePassword Boolean @default(false)`.
- `mfaEnabled Boolean @default(false)`, `mfaSecretEncrypted String?` — TOTP secret stored encrypted at rest; MFA required for SUPER_ADMIN (configurable per role in `SystemSetting`).
- `failedLoginAttempts Int @default(0)`, `lockedUntil DateTime?`, `lastLoginAt DateTime?` — login rate-limiting/lockout state (legacy gap.md P1: none existed).
- Relations: `roles UserRole[]`, `memberships WarehouseMembership[]`, `vendorLinks VendorUser[]`, `driverProfile Driver?`, `customerProfile Customer?`, `sessions Session[]`.
- Deletion: never hard-deleted; `DEACTIVATED` only. Every history table FKs to User with `Restrict`, which makes accidental deletion impossible anyway.

### Role
A named bundle of permissions. Data, not an enum, so Super Admin can manage roles without a migration (spec §4.1). Seeded with the ten spec roles: `SUPER_ADMIN`, `ADMIN`, `WAREHOUSE_ADMIN`, `WAREHOUSE_STAFF`, `RIDER`, `LINEHAUL_DRIVER`, `VENDOR`, `CUSTOMER`, `FINANCE`, `SUPPORT` (legacy `user_role` had 10 values but mixed orthogonal concepts — `dispatcher` folds into ADMIN/SUPPORT duties, and `micro_driver`/`big_driver` become Driver capabilities, §7 — audit §4).
- `code String @unique`, `name String`, `description String?`, `isSystem Boolean` (system roles cannot be deleted or renamed), `isActive Boolean`.

### Permission
One row per checkable capability, using the spec §21.2 naming: `warehouse.create`, `warehouse.read_all`, `warehouse.read_assigned`, `package.receive`, `package.dispatch`, `transfer.approve`, `delivery.confirm`, `finance.adjust`, `settlement.approve`, `user.manage`, `audit.read`, …
- `code String @unique`, `name String`, `module String` (grouping for the admin UI), `description String?`.

### RolePermission
Join of Role × Permission. `@@unique([roleId, permissionId])`. FKs `Cascade` (pure configuration; deleting a role removes its grants, and roles with users are archived instead — service-enforced).

### UserRole
Join of User × Role. A user may hold several roles (e.g. a person who is both RIDER and WAREHOUSE_STAFF); the *active* role for a request is resolved server-side per route, never taken from the client.
- `@@unique([userId, roleId])`, `assignedById → User (Restrict)`, `assignedAt`. FKs `Cascade` as configuration; revocation is a row delete **plus** an `AuditLog` entry and session refresh — permission removal takes effect immediately (spec §21.3).

### Session
Auth.js database session, extended for revocation and forensics.
- `sessionToken String @unique`, `userId → User (Cascade — sessions are ephemeral, not history)`, `expires DateTime`, `ipAddress String?`, `userAgent String?`, `createdAt`, `revokedAt DateTime?`.
- Index: `(userId, expires)`. Cookie is HTTP-only + Secure; the token itself is the only client artefact.

### WarehouseMembership
**Adopted almost as-is from the live-only legacy table** (audit §3.1) — it is the real warehouse-scoping mechanism the running system already uses (5 live rows) and exactly the spec's concept, which the repo SQL lacked entirely.
- `userId → User (Restrict)`, `warehouseId → Warehouse (Restrict)`, `roleId → Role (Restrict)` — the role the user holds *at that warehouse* (WAREHOUSE_ADMIN / WAREHOUSE_STAFF / RIDER home base); global roles (SUPER_ADMIN, ADMIN, FINANCE, SUPPORT) need no membership.
- `isPrimary Boolean @default(false)`, `assignedById → User (Restrict)`, `assignedAt`, `revokedAt DateTime?`, `revokedById → User (Restrict)`, `notes String?`.
- Partial unique index (migration SQL): one **active** (`revokedAt IS NULL`) membership per `(userId, warehouseId)`. Revocation is a timestamp, never a delete — assignment history is audit-relevant.

### UserInvitation
Covers both new-user onboarding and migrated-user password setup.
- `email String`, `roleId → Role (Restrict)`, `warehouseId → Warehouse (Restrict, nullable)`, `vendorId → Vendor (Restrict, nullable)`, `tokenHash String @unique` (only the hash is stored), `invitedById → User (Restrict)`, `expiresAt`, `acceptedAt DateTime?`, `status String` CHECK (`PENDING`, `ACCEPTED`, `EXPIRED`, `REVOKED`).

### VerificationToken
Password-reset and email-verification tokens (Auth.js pattern). `identifier String`, `tokenHash String`, `expires DateTime`, `@@unique([identifier, tokenHash])`. Rows are consumed (deleted) on use — tokens are not history.

## 2. Warehouses

### Warehouse
- `code String @unique` (e.g. `WH-KTM-01`), `name String`.
- `type String` CHECK in (`MAIN`, `REGIONAL`, `LOCAL_HUB`, `COLLECTION_CENTER`, `RETURN_CENTER`) — spec §5.1 (legacy had no type).
- `district String` — **first-class and required**. This closes the Phase 3c gap: the legacy routing design (same-district → last-mile, other-district → inter-warehouse) depended on `warehouses.district`, which was never applied to the live database (audit §3.3/§3.4). Also `city String`, `province String`, `country String @default("NP")`.
- `contactPhone String?`, `email String?`, `managerUserId → User (Restrict, nullable)` — spec §5.1 warehouse manager.
- `capacityPackages Int?`, `capacityWeightKg Decimal?` — hard/soft limits driving capacity warnings and dispatch blocks (spec §5.4, Scenario 16); occupancy is computed from open `InventoryRecord`s, never stored as a counter that can drift.
- `status String` CHECK (`ACTIVE`, `INACTIVE`, `ARCHIVED`) — deactivation only, never delete (§5.2).
- Indexes: `(district)`, `(status)`. Address detail lives in `WarehouseAddress`; the routing-critical fields (district/city) are denormalised onto Warehouse itself so route decisions never join for them.

### WarehouseAddress
One primary address per warehouse plus alternates (gate, billing). `warehouseId → Warehouse (Restrict)`, `kind String` (`PRIMARY`, `GATE`, `BILLING`), `addressLine1/2`, `city`, `district`, `province`, `postalCode String?`, `latitude/longitude Decimal?`. Partial unique: one `PRIMARY` per warehouse.

### WarehouseZone
Internal areas per spec §5.3. `warehouseId → Warehouse (Restrict)`, `code String` (e.g. `ZONE-A`), `name String`, `kind String` CHECK (`RECEIVING`, `INSPECTION`, `SORTING`, `STORAGE`, `DISPATCH`, `DAMAGED`, `RETURNS`), `capacityPackages Int?`, `isActive Boolean`. `@@unique([warehouseId, code])`.

### StorageLocation
Rack/shelf/bin level. `zoneId → WarehouseZone (Restrict)`, `rack String`, `shelf String?`, `bin String?`, `fullCode String @unique` — the canonical scannable code, e.g. `WH-KTM-01/ZONE-A/RACK-03/SHELF-02` (spec §5.3), `capacityPackages Int?`, `isActive Boolean`. Index: `(zoneId)`.

### WarehouseOperatingHours
`warehouseId → Warehouse (Cascade — pure configuration)`, `dayOfWeek Int` (0–6), `opensAt`/`closesAt` stored as minutes-from-midnight `Int` (avoids timezone-ambiguous `time` columns; display in Asia/Kathmandu), `isClosed Boolean`. `@@unique([warehouseId, dayOfWeek])`.

## 3. Vendors & customers

### Vendor
A business customer organisation (spec §14.1).
- `businessName String`, `registrationNumber String?` (PAN/VAT), `contactName String`, `email String?`, `phone String`.
- `verificationStatus String` CHECK in (`PENDING_VERIFICATION`, `UNDER_REVIEW`, `APPROVED`, `REJECTED`, `SUSPENDED`, `INACTIVE`) default `PENDING_VERIFICATION` — the legacy `vendors` table had only `is_active` and no verification lifecycle at all (audit §1.2). Only `APPROVED` vendors can create bookings (service-enforced).
- `verifiedById → User (Restrict)`, `verifiedAt DateTime?`, `verificationNotes String?`.
- `billingPreference String` (`PREPAID`, `CREDIT`, `COD_OFFSET`), `creditLimitPaisa BigInt?`.
- `isActive Boolean`. Deletion: never; status lifecycle only. Indexes: `(verificationStatus)`, `(businessName)`.

### VendorUser
Multiple authorised employees per vendor with intra-vendor roles (spec §14.2) — replaces the legacy single `users.vendor_id` column.
- `vendorId → Vendor (Restrict)`, `userId → User (Restrict)`, `vendorRole String` CHECK (`OWNER`, `MANAGER`, `BOOKING_STAFF`, `ACCOUNTS_STAFF`), `isActive Boolean`, `invitedById → User (Restrict)`. `@@unique([vendorId, userId])`.
- Every vendor-scoped query resolves the caller's vendor through this table server-side; a vendor user can never see another vendor's rows (spec Scenario: vendor A/B isolation, §26.3).

### VendorAddress
Pickup / billing / office addresses. `vendorId → Vendor (Restrict)`, `kind String` (`PICKUP`, `BILLING`, `OFFICE`), address fields mirroring WarehouseAddress plus `district String` (routing), `contactName`, `contactPhone`, `isApproved Boolean @default(false)` — vendors manage *approved* pickup addresses (spec §4.7); approval by Admin.

### Customer
A sender/recipient person record, deduplicated (spec §14.3). Recipients do **not** need an account to track a parcel — `userId` is optional.
- `fullName String`, `phone String`, `normalizedPhone String` (digits-only, country-code-normalised) with `@@unique` — the dedupe key; `email String? @unique` (nullable-unique in Postgres semantics).
- `userId → User (SetNull, nullable)` — link if the customer later registers; `SetNull` is safe here because the customer record itself is the surviving party record.
- `mergedIntoId → Customer (Restrict, self, nullable)` + `isMerged Boolean` — controlled duplicate resolution: the loser row is marked merged into the winner, never deleted, so historical orders keep pointing at a real row.
- Indexes: `(normalizedPhone)`, `(fullName)`.

### CustomerAddress
`customerId → Customer (Restrict)`, `kind String` (`PICKUP`, `DELIVERY`, `HOME`), address fields + `district`, `municipality String?`, `wardNumber String?`, `landmark String?` (spec §6.2 recipient addressing for Nepal), `isDefault Boolean`.

### CustomerContact
Additional contact channels beyond the primary phone/email. `customerId → Customer (Restrict)`, `kind String` (`PHONE`, `EMAIL`, `WHATSAPP`), `value String`, `isPrimary Boolean`, `verifiedAt DateTime?`.

## 4. Orders, shipments & packages

The legacy system's central flaw was two parallel generations of this model (audit §5, R6): v1 `orders`/`packages` (package = dimensions + POD, *no status*) versus v2 `shipments`/`driver_tasks` (the tracked parcel), with payment state duplicated in three places. The new model has exactly one chain, per spec §6.1:

**Order (booking request) → Shipment (consignment) → Package (physical parcel).**

### Order
- `orderNumber String @unique`, `vendorId → Vendor (Restrict, nullable)` (walk-in/admin bookings have no vendor), `customerId → Customer (Restrict, nullable)` (sender record), `createdById → User (Restrict)`, `createdByRole String` (role snapshot at creation — kept from legacy Phase 3a, which modelled this well).
- Sender snapshot: `senderName`, `senderPhone`, `senderEmail?` — snapshots, because the printed receipt must show what was declared even if the Customer record is later corrected.
- `originWarehouseId → Warehouse (Restrict, nullable)` (null until intake/routing assigns it), `destinationDistrict String`, `destinationServiceAreaId → ServiceArea (Restrict, nullable)`.
- `approvalStatus String` CHECK (`PENDING`, `APPROVED`, `REJECTED`) default `APPROVED` for staff-created, `PENDING` for vendor-submitted workflow orders (legacy Phase 3a pattern, retained); `approvedById → User (Restrict)`, `approvedAt`, `approvalNote`.
- `status String` CHECK (`DRAFT`, `SUBMITTED`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`).
- Cancellation block (spec §6.4): `cancelRequestedById`, `cancelApprovedById`, `cancelReason`, `cancelStage` (shipment stage at cancellation), `cancelChargesPaisa BigInt @default(0)`, `cancelledAt`. Cancellation after pickup does not cancel in place — it spawns the return workflow (Scenario 9); the service enforces which path applies.
- `paymentMethod String` (configurable set, §8), `paymentStatus String` CHECK (`UNPAID`, `PENDING`, `PARTIAL`, `PAID`, `REFUNDED`, `PARTIALLY_REFUNDED`, `DISPUTED`) — order-level roll-up only; the *authoritative* money records are `Payment`/`LedgerTransaction` (§8). This kills the legacy three-sources-of-truth problem: order/shipment/package payment columns are derived caches, recomputed by the finance service, never written by UI code.
- `pickupMethod String` (`RIDER_PICKUP`, `WAREHOUSE_DROPOFF`), `pickupAddressId → VendorAddress/CustomerAddress` (modelled as nullable FKs to each + a service check that exactly one is set), `deliveryInstructions String?`, `notes String?`, `scheduledAt DateTime?`.
- Indexes: `(vendorId, createdAt)`, `(customerId)`, `(approvalStatus)`, `(status, createdAt)`, `(destinationDistrict)`.

### OrderItem
What was booked, line by line. `orderId → Order (Cascade — composition, draft-editable)`, `description String`, `quantity Int` (CHECK > 0), `unitPricePaisa BigInt?`, `weightKg Decimal?`, `sku String?`. Items describe intent; physical contents live in `PackageItem`.

### Shipment
The consignment moving under one contract — normally 1 per Order, but an Order may split into several Shipments, and returns/exchanges are Shipments too (spec §12: a return must not erase the original; it is a *separate linked shipment*).
- `shipmentNumber String @unique`, `orderId → Order (Restrict)`.
- `kind String` CHECK (`FORWARD`, `RETURN`, `EXCHANGE`), `originalShipmentId → Shipment (Restrict, self, nullable)` — RETURN/EXCHANGE shipments point at the shipment they reverse/replace.
- `originWarehouseId → Warehouse (Restrict)`, `destinationWarehouseId → Warehouse (Restrict, nullable)`, `destinationServiceAreaId → ServiceArea (Restrict, nullable)`, `routeKind String` CHECK (`LAST_MILE`, `INTER_WAREHOUSE`) — decided by district comparison (origin warehouse district vs destination district), the Phase 3 routing rule, now computable because `Warehouse.district` exists.
- `shippingServiceId → ShippingService (Restrict)`, `pricingRuleId → PricingRule (Restrict, nullable)` + **charge snapshots**: `shippingChargePaisa BigInt`, `codAmountPaisa BigInt @default(0)` — the price *as quoted at booking* is frozen on the shipment even if the PricingRule later changes (spec §6.3: no hardcoded prices; tariff is configuration, history is fact).
- `status String` — a **roll-up derived from its Packages** (`ACTIVE`, `PARTIALLY_DELIVERED`, `DELIVERED`, `RETURNED`, `CANCELLED`), recomputed by the package lifecycle service on every package transition (Scenario 13: 3 of 5 packages delivered ⇒ shipment `PARTIALLY_DELIVERED`). Never set directly by users.
- `expectedDeliveryAt DateTime?`, `totalWeightKg Decimal?`.
- Indexes: `(orderId)`, `(originWarehouseId, status)`, `(destinationWarehouseId, status)`.

### Package
**The canonical physical parcel** — the merger of legacy `packages` (dimensions, POD) and legacy `shipments` (status, custody, tracking). One row per physical box, each with its own tracking ID and history (spec §6.1: ORD-1001 → SHP-1001 → PKG-1001…1005).
- `trackingId String @unique` — the public tracking code printed on the label and used on the no-login tracking page.
- `shipmentId → Shipment (Restrict)`, `orderId → Order (Restrict)` (denormalised for direct lookup; always equals `shipment.orderId`, maintained by the service).
- Recipient snapshot: `recipientName`, `recipientPhone`, `recipientAltPhone?`, `recipientEmail?`, delivery address block (`deliveryAddress`, `deliveryCity`, `deliveryDistrict`, `municipality?`, `wardNumber?`, `landmark?`, `deliveryLatitude/Longitude Decimal?`) — snapshotted per package because packages from one shipment can be re-routed/corrected individually after dispatch only via exception (spec §6.4).
- Weights (spec §6.3): `declaredWeightKg`, `actualWeightKg?`, `volumetricWeightKg?`, `billableWeightKg?` (all `Decimal`), `weightMeasuredById → User (Restrict)`, `weightMeasuredAt`. Dimensions: `lengthCm/widthCm/heightCm Decimal?`.
- `declaredValuePaisa BigInt?`, `description String`, `category String` (`DOCUMENT`, `PACKAGE`, `FRAGILE`, `PERISHABLE`, `LIQUID`, `OTHER` — legacy `parcel_type` set), `isFragile Boolean`, `handlingInstructions String?`, `restrictedGoodsDeclared Boolean @default(false)`.
- `codAmountPaisa BigInt @default(0)` — this package's share of COD; per-package COD is what makes partial delivery settle correctly (Scenario 13).
- `currentWarehouseId → Warehouse (Restrict, nullable)` — where the package physically is, or `null` while in a custodian's hands/in transit; always consistent with the open `InventoryRecord`/`PackageCustody` (invariants in the ER document).
- Five separate status fields — §5 below.
- `version Int @default(1)` (optimistic locking, Scenario 8).
- Indexes: `(shipmentId)`, `(currentWarehouseId, operationalStatus)`, `(operationalStatus, createdAt)`, `(recipientPhone)` for support lookups. Tracking-page lookup is by `trackingId` + a verification factor (spec §4.8) — never by sequential ID.

### PackageItem
Physical contents of one package. `packageId → Package (Cascade — composition)`, `orderItemId → OrderItem (Restrict, nullable)` (which booked line this fulfils), `description String`, `quantity Int`, `declaredValuePaisa BigInt?`.

### PackageLabel
`packageId → Package (Restrict)`, `labelCode String @unique` (barcode payload), `qrPayload String`, `fileId → FileAsset (Restrict, nullable)` (rendered PDF), `printCount Int @default(0)`, `lastPrintedAt`, `lastPrintedById → User (Restrict)`. Regenerating a label never changes `trackingId`.

### DeliveryInstruction
Free-standing instructions attached to an order/shipment leg. `orderId → Order (Cascade)`, `shipmentId → Shipment (Restrict, nullable)`, `kind String` (`PICKUP`, `DELIVERY`, `HANDLING`), `instructions String`, `createdById → User (Restrict)`.

### TrackingEvent — append-only
The single unified history, replacing **four** fragmented legacy trails (`delivery_status_history`, `shipment_events`, `scan_events`, `order_events` — audit §5) which used free-text events, no prev/new status pair, and no idempotency.
- Subject: `packageId → Package (Restrict, nullable)`, `shipmentId → Shipment (Restrict, nullable)`, `orderId → Order (Restrict, nullable)`; `subjectType String` CHECK (`PACKAGE`, `SHIPMENT`, `ORDER`) with a DB CHECK that exactly the matching FK is set. Package events are the norm (spec §7.4); order/shipment events cover approval, cancellation, roll-up changes.
- `eventType String` — controlled vocabulary from the domain module (e.g. `BOOKED`, `RECEIVED`, `INSPECTED`, `SORTED`, `LOADED`, `DISPATCHED`, `ARRIVED`, `OUT_FOR_DELIVERY`, `DELIVERY_ATTEMPTED`, `DELIVERED`, `COD_COLLECTED`, `EXCEPTION_RAISED`, `CUSTODY_TRANSFERRED`).
- `previousStatus String?`, `newStatus String?` — the operational-status pair for package events (spec §7.4).
- `occurredAt DateTime` (event time, may come from an offline device), `createdAt` (server recorded time).
- `actorId → User (Restrict, nullable)`, `actorRole String?` (snapshot — the legacy `dev-bypass` actor in live data, audit §2, is exactly what this must never contain; system events use `actorId = null` + `source = SYSTEM`).
- Context: `warehouseId → Warehouse (Restrict)`, `storageLocationId → StorageLocation (Restrict)`, `transferId → Transfer (Restrict)`, `tripId → Trip (Restrict)`, `deliveryAssignmentId → DeliveryAssignment (Restrict)` — all nullable, all Restrict.
- `notes String?`, `evidenceFileId → FileAsset (Restrict, nullable)`, `source String` (`WEB`, `SCANNER`, `MOBILE`, `SYSTEM`, `OFFLINE_SYNC`), `idempotencyKey String? @unique` — an offline device retrying a sync, or a double scan, returns the existing event instead of writing a second one (Scenarios 7, 10).
- Indexes: `(packageId, occurredAt)`, `(shipmentId, occurredAt)`, `(orderId, occurredAt)`, `(actorId, createdAt)`, `(eventType, createdAt)`. **No `updatedAt`. No delete path.** The legacy `log_order_status_change` trigger's unattributed-writes flaw (audit R9: `changed_by` was NULL for all backend writes) is fixed by making the *service* — the only writer — always supply the actor.

## 5. Package status model (spec §7.1–7.3)

Five independent fields on `Package`. Conflating them was a legacy defect: e.g. a package can be operationally `RECEIVED_AT_DESTINATION`, physically `DAMAGED`, and have an active `DAMAGED` exception simultaneously (spec §7.2).

### `operationalStatus` — the 20-state lifecycle (§7.1) + two pre-lifecycle terminals
`DRAFT` and `CANCELLED` sit alongside the 20 (a cancelled booking never enters the chain). Allowed values, in chain order:

1. `BOOKED` 2. `PICKUP_ASSIGNED` 3. `PICKUP_IN_PROGRESS` 4. `PICKED_UP` 5. `RECEIVED_AT_ORIGIN` 6. `INSPECTION_PENDING` 7. `PROCESSING` 8. `SORTED` 9. `READY_FOR_DISPATCH` 10. `TRANSFER_ASSIGNED` 11. `DISPATCHED` 12. `IN_TRANSIT` 13. `ARRIVED_AT_DESTINATION` 14. `RECEIVING_INSPECTION` 15. `RECEIVED_AT_DESTINATION` 16. `READY_FOR_DELIVERY` 17. `DELIVERY_ASSIGNED` 18. `OUT_FOR_DELIVERY` 19. `DELIVERY_ATTEMPTED` 20. `DELIVERED`

Plus `DRAFT`, `CANCELLED`. Last-mile-only shipments legitimately skip the transfer block (10–15) — the transition table, not the column, defines legal paths. Transitions live in an explicit state-transition table in the domain layer (`PackageLifecycleService`), unit-tested for every allowed *and* disallowed pair (spec §7.3, §26.1): e.g. `DELIVERED` is unreachable except from `DELIVERY_ATTEMPTED`/`OUT_FOR_DELIVERY` with a `ProofOfDelivery`; `RECEIVED_AT_*` is unreachable without a receiving `TransferScan`/intake scan; no transition ever fires without a `TrackingEvent` + custody/inventory updates in the same database transaction.

### `condition` — physical state
`GOOD`, `DAMAGED`, `PACKAGING_COMPROMISED`. Set at receiving/inspection scans with photo evidence (`PackageCondition` history is derivable from TrackingEvents of type `CONDITION_RECORDED`; a separate condition-history table was considered and rejected as duplication — the event trail already stores actor, time, warehouse and evidence).

### `paymentStatus` — this package's money state
`NOT_APPLICABLE`, `PENDING`, `PAID`, `COD_DUE`, `COD_COLLECTED`, `COD_REMITTED`, `COD_SETTLED`, `REFUNDED`. Derived by the finance service from `Payment`/`CODCollection` rows; never edited directly.

### `deliveryStatus` — final-mile state
`NOT_STARTED`, `ASSIGNED`, `OUT_FOR_DELIVERY`, `ATTEMPTED`, `DELIVERED`, `FAILED`, `REFUSED`, `RETURN_INITIATED`, `RETURNED_TO_WAREHOUSE`, `RETURNED_TO_SENDER`.

### `exceptionStatus` — active problem track (§7.2)
`NONE`, `ON_HOLD`, `ADDRESS_CLARIFICATION_REQUIRED`, `DAMAGED`, `MISSING`, `MISROUTED`, `DELAYED`, `CUSTOMER_UNAVAILABLE`, `RECIPIENT_REFUSED`, `DELIVERY_FAILED`, `PICKUP_FAILED`, `RETURN_REQUESTED`, `RETURN_APPROVED`, `LOST_UNDER_INVESTIGATION`, `RESOLVED` (transient marker before returning to `NONE` with the resolution recorded on the linked `Incident`). Raising an exception creates/links an `Incident` (§9); an exception never overwrites `operationalStatus`.

## 6. Inventory & custody

Parcel inventory and supplies inventory are **separate models** (spec §8.2). The legacy system conflated them: its `inventory` table was defined as SKU stock, then repurposed live into a parcel-intake register (audit §3.3). That conflation ends here.

### InventoryRecord — parcel inventory (one row per warehouse stay)
A package has one `InventoryRecord` per continuous stay at a warehouse. `releasedAt = null` means *physically there now*.
- `packageId → Package (Restrict)`, `warehouseId → Warehouse (Restrict)`, `storageLocationId → StorageLocation (Restrict, nullable)` (null between receiving dock and put-away).
- `receivingEventId → TrackingEvent (Restrict)` — the scan that created this stay; a package cannot be in inventory without one (spec §7.3).
- `receivedAt`, `receivedById → User (Restrict)`, `conditionOnArrival String` (mirrors `Package.condition` at intake), `releasedAt DateTime?`, `releasedById → User (Restrict)`, `releaseReason String?` (`DISPATCH`, `DELIVERY_HANDOUT`, `TRANSFER`, `RETURN`, `CORRECTION`).
- Partial unique index (migration SQL): **one open record (`releasedAt IS NULL`) per `packageId`** — a package can never be in two warehouses' stock at once. Indexes: `(warehouseId, releasedAt)`, `(packageId, receivedAt)`, `(storageLocationId, releasedAt)`.
- A package out with a rider has **no** open InventoryRecord — it appears in custody, not stock (spec §8.1).

### InventoryMovement — append-only
Every physical/logical movement of a parcel inside or between locations (spec §8.3): `RECEIVING`, `PUT_AWAY`, `INTERNAL_MOVE`, `PICKING`, `DISPATCH`, `TRANSFER_OUT`, `TRANSFER_IN`, `RETURN_RECEIVING`, `DAMAGE_QUARANTINE`, `CORRECTION`.
- `packageId → Package (Restrict)`, `inventoryRecordId → InventoryRecord (Restrict, nullable)`, `fromWarehouseId/toWarehouseId → Warehouse (Restrict)`, `fromLocationId/toLocationId → StorageLocation (Restrict)`, `actorId → User (Restrict)`, `reason String?`, `trackingEventId → TrackingEvent (Restrict, nullable)`, `createdAt`. Indexes: `(packageId, createdAt)`, `(toWarehouseId, createdAt)`.

### PackageCustody — append-only custody chain
Who is accountable for the package *right now* is the open row (`endedAt IS NULL`); history is the closed rows.
- `packageId → Package (Restrict)`, `custodianType String` CHECK (`WAREHOUSE`, `USER`, `RECIPIENT`, `RETURN_TEAM`), `custodianUserId → User (Restrict, nullable)` (rider/staff), `warehouseId → Warehouse (Restrict, nullable)`, `storageLocationId → StorageLocation (Restrict, nullable)` — a DB CHECK enforces exactly the fields matching `custodianType` are set.
- `startedAt`, `endedAt DateTime?`, `handoverId → CustodyHandover (Restrict, nullable)` (the handover that began this custody; null only for the initial booking custody), `trackingEventId → TrackingEvent (Restrict, nullable)`.
- Partial unique index: **one open custody per `packageId`**. This is the database-level statement of "every package has exactly one accountable custodian" (spec closing principle).

### CustodyHandover + HandoverBatch
- `HandoverBatch`: one physical handover act covering many packages (a rider collecting 25 parcels, a warehouse receiving a trip). `fromCustodianType/fromUserId/fromWarehouseId`, `toCustodianType/toUserId/toWarehouseId` (same shape as custody), `expectedCount Int`, `confirmedCount Int @default(0)`, `status String` CHECK (`PENDING`, `PARTIALLY_CONFIRMED`, `CONFIRMED`, `DISPUTED`), `initiatedById → User (Restrict)`, `confirmedById → User (Restrict, nullable)`, `evidenceFileId → FileAsset (Restrict, nullable)`, `createdAt`, `confirmedAt`. If `confirmedCount ≠ expectedCount` when the batch is closed, the service **must** open an `Incident` (`HANDOVER_DISCREPANCY`) for the difference — the 25-vs-23 case in spec §8.4 can never be silently absorbed.
- `CustodyHandover` (line): `batchId → HandoverBatch (Restrict)`, `packageId → Package (Restrict)`, `fromCustodyId → PackageCustody (Restrict)`, `toCustodyId → PackageCustody (Restrict, nullable until confirmed)`, `status String` (`PENDING`, `CONFIRMED`, `MISSING`, `DAMAGED`), `confirmedAt`. `@@unique([batchId, packageId])`.

### StockItem — supplies catalogue (kept strictly separate from parcels)
Boxes, tape, labels, bags (spec §8.2). `warehouseId → Warehouse (Restrict)`, `sku String`, `name String`, `unit String` (`PCS`, `ROLL`, `KG`), `quantityOnHand Int @default(0)` (maintained transactionally from movements; CHECK ≥ 0), `reorderLevel Int @default(0)`, `isActive Boolean`. `@@unique([warehouseId, sku])` — the one legacy constraint worth keeping verbatim (audit §1.6).

### StockMovement — append-only supplies ledger
Adopts the design of the live-only legacy `inventory_movements` table (audit §3.1 — designed but never used). `stockItemId → StockItem (Restrict)`, `warehouseId → Warehouse (Restrict)`, `type String` (`PURCHASE`, `ISSUE`, `RETURN`, `ADJUSTMENT`, `DAMAGE_WRITE_OFF`), `quantityDelta Int`, `quantityBefore Int`, `quantityAfter Int` (before/after snapshots make the ledger self-auditing), `reason String?`, `reference String?` (purchase invoice no.), `performedById → User (Restrict)`, `createdAt`. Index: `(stockItemId, createdAt)`.

## 7. Transfers & transport

The legacy model stored one `warehouse_transfers` row **per shipment** with only 3 states and no reconciliation (audit §1.4). The new model is a proper header/lines design with the spec §9.3 fifteen-state lifecycle.

### Transfer
- `transferNumber String @unique`, `originWarehouseId → Warehouse (Restrict)`, `destinationWarehouseId → Warehouse (Restrict)` (CHECK origin ≠ destination).
- `status String` CHECK: `DRAFT`, `REQUESTED`, `APPROVED`, `REJECTED`, `PREPARING`, `READY_FOR_DISPATCH`, `DISPATCHED`, `IN_TRANSIT`, `ARRIVED`, `PARTIALLY_RECEIVED`, `RECEIVED`, `RECONCILIATION_PENDING`, `RECONCILED`, `CLOSED`, `EXCEPTION`, `CANCELLED` (spec §9.3's fifteen plus `CANCELLED`).
- `driverId → Driver (Restrict, nullable)` (line-haul), `vehicleId → Vehicle (Restrict, nullable)`, `tripId → Trip (Restrict, nullable, unique — one trip executes one transfer)`, `dispatchSupervisorId → User (Restrict, nullable)`.
- `createdById → User (Restrict)`, `approvedById → User (Restrict, nullable)`, `approvedAt`, `expectedArrivalAt`, `dispatchedAt`, `arrivedAt`, `reconciledAt`, `closedAt`, `instructions String?`.
- `version Int @default(1)`. Indexes: `(originWarehouseId, status)`, `(destinationWarehouseId, status)`, `(driverId, status)`.
- Closure invariant: `CLOSED` requires `RECONCILED`, which requires every `TransferItem` to be `RECEIVED` or resolved through an approved `Incident` — enforced by `TransferService`, with counts denormalised nowhere (always counted from items).

### TransferItem
- `transferId → Transfer (Restrict)`, `packageId → Package (Restrict)`, `@@unique([transferId, packageId])`.
- `expectedCondition String`, `itemStatus String` CHECK (`EXPECTED`, `LOADED`, `IN_TRANSIT`, `RECEIVED`, `MISSING`, `DAMAGED`, `EXCESS`, `WRONG_PACKAGE`), `receivedCondition String?`, `receivedById → User (Restrict)`, `receivedAt`, `discrepancyNote String?`, `incidentId → Incident (Restrict, nullable)` — every non-clean outcome links its investigation.
- Partial unique index: a package may appear on only one **open** transfer at a time (prevents double-dispatch, Scenario 8).

### TransferManifest
The frozen loading document. `transferId → Transfer (unique, Restrict)`, `manifestCode String @unique`, `generatedById → User (Restrict)`, `generatedAt`, `packageCount Int`, `totalWeightKg Decimal`, `sealedAt DateTime?` — once sealed, items cannot change except by an authorised amendment that writes a `TrackingEvent` + `AuditLog` (spec §4.6: no silent manifest edits after dispatch). Absorbs the useful live-only columns of legacy `trip_manifests` (loaded/received by/at, exception fields) — those live on `TransferItem`/`TransferScan` in the new model, where they belong per-package rather than per-manifest-row.

### TransferScan — append-only
Every physical scan during loading/unloading. `transferItemId → TransferItem (Restrict)`, `scanType String` (`LOAD`, `UNLOAD`, `RECHECK`), `warehouseId → Warehouse (Restrict)`, `scannedById → User (Restrict)`, `scannedAt`, `idempotencyKey String @unique` — a duplicate scan (Scenario 7) hits the unique key and returns the original scan with a clear "already scanned" result instead of double-counting inventory.

### Trip
One line-haul journey executing one Transfer.
- `tripNumber String @unique`, `transferId → Transfer (unique, Restrict)`, `driverId → Driver (Restrict)`, `vehicleId → Vehicle (Restrict)`.
- `status String` CHECK: `PLANNED`, `ASSIGNED`, `LOADING`, `DISPATCHED`, `IN_TRANSIT`, `DELAYED`, `ARRIVED`, `UNLOADING`, `COMPLETED`, `CANCELLED`, `INCIDENT` (spec §10.5).
- `plannedDepartureAt`, `actualDepartureAt`, `expectedArrivalAt`, `actualArrivalAt`. Manual checkpoints (`TripStop`) are the reliable progress mechanism; GPS is optional garnish (spec §10.5).
- Indexes: `(driverId, status)`, `(vehicleId, status)`.

### TripStop
Replaces legacy `checkpoints`. `tripId → Trip (Restrict)`, `sequence Int`, `label String`, `latitude/longitude Decimal?`, `plannedAt?`, `passedAt?`, `recordedById → User (Restrict)`, `notes String?`. `@@unique([tripId, sequence])`.

### Vehicle
- `registration String @unique`, `type String` CHECK (`BIKE`, `CAR`, `VAN`, `TRUCK`, `PICKUP`), `capacityKg Decimal?`, `capacityVolumeM3 Decimal?`, `homeWarehouseId → Warehouse (Restrict, nullable)`.
- `status String` CHECK (`AVAILABLE`, `ASSIGNED`, `ON_TRIP`, `MAINTENANCE`, `OFFLINE`) — replaces legacy `is_active` + Phase 3b `status` pair.
- `insuranceExpiry Date?`, `registrationExpiry Date?`, `inspectionStatus String` (`VALID`, `DUE`, `EXPIRED`), `assignedDriverId → Driver (SetNull, nullable)` — assignment must never block driver archival. The service refuses trip assignment for expired/unavailable vehicles (spec §10.4).

### VehicleMaintenance
`vehicleId → Vehicle (Restrict)`, `kind String` (`SCHEDULED`, `REPAIR`, `INSPECTION`), `scheduledAt`, `completedAt?`, `costPaisa BigInt?`, `notes String?`, `nextDueAt Date?`, `recordedById → User (Restrict)`.

### Driver
The operational profile; the login identity is the linked `User` (1:1). Replaces legacy `drivers` and absorbs its `driver_type`.
- `userId → User (unique, Restrict)`, `homeWarehouseId → Warehouse (Restrict)`.
- `licenseNumber String`, `licenseCategory String?`, `licenseExpiry Date`, `profilePhotoFileId → FileAsset (Restrict, nullable)`, `emergencyContactName String?`, `emergencyContactPhone String?` — documents/expiry/emergency contact were absent in legacy (audit §5) and are required by spec §10.1. Document files themselves are `FileAsset`s linked via `FileAsset.entityType = DRIVER`.
- `employmentStatus String` CHECK (`ACTIVE`, `ON_LEAVE`, `SUSPENDED`, `INACTIVE`), `availabilityStatus String` CHECK (`AVAILABLE`, `ASSIGNED`, `ON_PICKUP`, `ON_DELIVERY`, `ON_TRIP`, `OFF_DUTY`, `ON_LEAVE`, `SUSPENDED`, `INACTIVE`) — spec §10.3; updated by assignment services from real work, never by "is logged in".
- `currentTripId → Trip (Restrict, nullable)`, `lastSeenAt DateTime?` (from GPS pings).
- Indexes: `(homeWarehouseId, availabilityStatus)`, `(licenseExpiry)` (expiry alerts).

### DriverCapability
Capability-based assignment (spec §10.2) replacing the single legacy `driver_type` text: `driverId → Driver (Cascade — composition)`, `capability String` CHECK (`PICKUP`, `DELIVERY`, `LINEHAUL`), `@@unique([driverId, capability])`. Legacy mapping: `micro` → {PICKUP, DELIVERY}, `big` → {LINEHAUL}. A rider without `LINEHAUL` can never be assigned a Trip — checked in `TripService`, not in the UI.

### GpsPing (retained, slimmed)
Legacy `gps_tracking` carried over because live tracking screens depend on it: `driverId → Driver (Restrict)`, `tripId → Trip (Restrict, nullable)`, `deliveryAssignmentId → DeliveryAssignment (Restrict, nullable)`, `latitude/longitude Decimal`, `speedKmh Decimal?`, `recordedAt`, `createdAt`. Index `(driverId, recordedAt)`. Retention is a `JobRecord`-driven job (default 30 days, configurable) replacing the legacy hard-delete function `cleanup_gps_tracking()` — with the difference that retention is a *configured policy on operational telemetry*, not a deletion of business history.

## 8. Delivery

### DeliveryBatch
A rider's grouped run for a shift/area (spec §11.2). `riderId → Driver (Restrict)`, `warehouseId → Warehouse (Restrict)`, `serviceAreaId → ServiceArea (Restrict, nullable)`, `batchDate Date`, `kind String` (`PICKUP`, `DELIVERY`, `MIXED`), `status String` (`OPEN`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`), `createdById → User (Restrict)`. Index `(riderId, batchDate)`.

### DeliveryAssignment
One package ↔ one rider task, unifying legacy v1 `delivery_assignments` (per-order) and v2 `driver_tasks` (per-shipment) into a single per-**package** assignment system (audit §5).
- `packageId → Package (Restrict)`, `driverId → Driver (Restrict)`, `batchId → DeliveryBatch (Restrict, nullable)`, `vehicleId → Vehicle (Restrict, nullable)`.
- `kind String` CHECK (`PICKUP`, `DELIVERY`), `status String` CHECK (`PENDING`, `ACCEPTED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, `CANCELLED`, `REASSIGNED`).
- `assignedById → User (Restrict)`, `assignedAt`, `acceptedAt`, `startedAt`, `completedAt`, `routeSequence Int?`, `routeDistanceM Int?`, `routeDurationS Int?`, `routeGeometry Json?` (provider output cached; MapTiler→ORS as in legacy), `deliveryInstructions String?`.
- `reassignedFromId → DeliveryAssignment (Restrict, self, nullable)` — reassignment (Scenario 14) creates a new assignment chained to the old one plus a custody handover; history is never rewritten.
- `version Int @default(1)`. Indexes: `(driverId, status)`, `(packageId, status)`, `(batchId)`. Partial unique index: one active (`PENDING/ACCEPTED/IN_PROGRESS`) assignment per package per kind.

### DeliveryAttempt — append-only
Replaces the legacy `failed_attempts` **counter** on `driver_tasks` (audit §1.4) with real per-attempt records (spec §11.3).
- `assignmentId → DeliveryAssignment (Restrict)`, `packageId → Package (Restrict)`, `attemptNumber Int` (`@@unique([assignmentId, attemptNumber])`), `attemptedAt`, `latitude/longitude Decimal?`.
- `result String` CHECK (`DELIVERED`, `RECIPIENT_UNAVAILABLE`, `PHONE_UNREACHABLE`, `WRONG_ADDRESS`, `REFUSED`, `BUSINESS_CLOSED`, `AREA_INACCESSIBLE`, `PAYMENT_UNAVAILABLE`, `PACKAGE_DAMAGED`, `PICKUP_FAILED`, `OTHER`), `failureReason String?`, `contactOutcome String?`, `evidenceFileId → FileAsset (Restrict, nullable)`, `nextAction String` (`REDELIVER`, `ADDRESS_CORRECTION`, `SUPPORT_ESCALATION`, `RETURN_TO_SENDER`, `RETURN_TO_WAREHOUSE`, `NONE`), `recordedById → User (Restrict)`.

### ProofOfDelivery
The evidence that makes `DELIVERED` legal (spec §11.4, §7.3).
- `packageId → Package (unique while valid — one accepted POD per package; a superseded POD is kept with `supersededById` self-FK for dispute history)`, `assignmentId → DeliveryAssignment (Restrict)`, `attemptId → DeliveryAttempt (Restrict, nullable)`.
- `method String` CHECK (`OTP`, `SIGNATURE`, `PHOTO`, `AUTHORISED_PERSON`) — configurable per service in `SystemSetting`; `receivedByName String?`, `relationshipToRecipient String?`.
- OTP: `otpCodeHash String?`, `otpExpiresAt DateTime?`, `otpVerifiedAt DateTime?` — only the hash is stored; the code is delivered to the recipient by notification.
- `signatureFileId → FileAsset (Restrict)`, `photoFileId → FileAsset (Restrict)`, `latitude/longitude Decimal?`, `deliveredAt`, `recordedById → User (Restrict)`.
- Invariant: `Package.operationalStatus = DELIVERED` requires a non-superseded ProofOfDelivery **or** an authorised exception — an `Approval` (§9) of type `DELIVERY_WITHOUT_PROOF` linked from the delivering TrackingEvent. There is no third path.

## 9. Finance (spec Part 13)

Design spine: **COD is a liability, never revenue** (§13.1); **the ledger is immutable** — corrections are new linked rows, never edits (§13.5, §4.9); **every mutation is idempotent** (Scenario 12; audit R8).

### FinancialAccount
Chart-of-accounts-lite. `code String @unique` (e.g. `SHIPPING_REVENUE`, `COD_CLEARING`, `VENDOR_PAYABLE`, `DRIVER_CASH`, `CASH_ON_HAND`, `BANK`, `REFUNDS_CLEARING`), `name String`, `kind String` (`ASSET`, `LIABILITY`, `REVENUE`, `EXPENSE`), `ownerType String` (`COMPANY`, `VENDOR`, `DRIVER`), `ownerVendorId → Vendor (Restrict, nullable)`, `ownerDriverId → Driver (Restrict, nullable)`, `currency @default("NPR")`, `isActive Boolean`. Balances are **derived** by summing `LedgerTransaction`s — never a stored, overwritable number (spec §13.5).

### LedgerTransaction — append-only, immutable
- `reference String @unique` (human/ops reference, e.g. `TXN-2026-000123`).
- `accountId → FinancialAccount (Restrict)`, `direction String` CHECK (`DEBIT`, `CREDIT`), `amountPaisa BigInt` (CHECK > 0), `currency @default("NPR")`.
- `type String` (`SHIPPING_CHARGE`, `PAYMENT_RECEIVED`, `COD_COLLECTED`, `COD_REMITTED`, `COD_SETTLED`, `REFUND`, `ADJUSTMENT`, `REVERSAL`, `DRIVER_PAYOUT`).
- Links: `orderId → Order (Restrict)`, `packageId → Package (Restrict)`, `paymentId → Payment (Restrict)`, `codCollectionId → CODCollection (Restrict)`, `settlementId → VendorSettlement (Restrict)` — all nullable, at least the relevant one set (service-enforced).
- `paymentMethod String?`, `occurredAt`, `actorId → User (Restrict)`, `approvedById → User (Restrict, nullable)`.
- `reversalOfId → LedgerTransaction (Restrict, self, nullable)` with a **unique** index — an entry can be reversed at most once, by a new `REVERSAL` entry of opposite direction; the original is never modified or deleted. `adjustmentId → FinancialAdjustment (Restrict, nullable)`.
- `idempotencyKey String? @unique`, `createdAt` only. Indexes: `(accountId, createdAt)`, `(orderId)`, `(type, createdAt)`.

### Invoice
- `invoiceNumber String @unique`, `orderId → Order (Restrict, nullable)`, `vendorId → Vendor (Restrict, nullable)` (vendor periodic invoices), `customerId → Customer (Restrict, nullable)`.
- `subtotalPaisa`, `discountPaisa @default(0)`, `taxPaisa @default(0)`, `totalPaisa` (all `BigInt`), `currency @default("NPR")`.
- `status String` CHECK (`DRAFT`, `ISSUED`, `PARTIALLY_PAID`, `PAID`, `OVERDUE`, `CANCELLED`, `REFUNDED`) — status is recomputed from allocations by the finance service.
- `issuedAt`, `dueAt Date?`, `issuedById → User (Restrict)`, `notes String?`. Indexes: `(vendorId, issuedAt)`, `(status, dueAt)`.

### Payment
A single act of paying, independent of what it settles.
- `orderId → Order (Restrict, nullable)`, `invoiceId → Invoice (Restrict, nullable)`, `payerType String` (`CUSTOMER`, `VENDOR`, `COMPANY`), `payerCustomerId/payerVendorId` nullable FKs (Restrict).
- `amountPaisa BigInt`, `currency @default("NPR")`, `method String` — configurable value set from `SystemSetting` seeded with spec §13.2 (`CASH`, `BANK_TRANSFER`, `MOBILE_WALLET`, `ONLINE_GATEWAY`, `PREPAID_BALANCE`, `CREDIT_ACCOUNT`); the legacy `upi` value (audit R10) is dropped. **No card data is ever stored** — gateway payments keep only the provider reference.
- `status String` CHECK (`PENDING`, `PARTIALLY_PAID` n/a at payment level — kept for parity where a gateway confirms in parts, `PAID`, `FAILED`, `REFUNDED`, `PARTIALLY_REFUNDED`, `DISPUTED`, `REVERSED`) per spec §13.3.
- `transactionRef String?` with a **partial unique index where not null** — the legacy `payments.transaction_ref` had no uniqueness (audit R8); duplicate gateway callbacks now collide safely. `idempotencyKey String? @unique`.
- `paidAt DateTime?`, `recordedById → User (Restrict)`, `gatewayProvider String?`, `gatewayPayload Json?` (non-sensitive callback metadata).
- Indexes: `(orderId)`, `(status, createdAt)`.

### PaymentAllocation
Splits one Payment across Invoices (and records the unallocated remainder implicitly). `paymentId → Payment (Restrict)`, `invoiceId → Invoice (Restrict)`, `amountPaisa BigInt`, `allocatedById → User (Restrict)`, `createdAt`. `@@unique([paymentId, invoiceId])`. Service invariant: Σ allocations ≤ payment amount; invoice status derives from Σ allocations vs `totalPaisa`.

### CODCollection
One rider collection from one recipient for one package (spec §13.4 steps 4–7).
- `packageId → Package (Restrict)`, `shipmentId → Shipment (Restrict)`, `deliveryAssignmentId → DeliveryAssignment (Restrict)`, `collectedByDriverId → Driver (Restrict)`.
- `amountPaisa BigInt` — the amount **as collected and declared at the door**; this figure is never edited afterwards (Scenario 5: collected Rs 5,000 stays Rs 5,000 forever; the Rs 4,500 appears on the remittance).
- `method String` (`CASH`, `MOBILE_WALLET`, `BANK_TRANSFER`), `collectedAt`, `remittanceId → DriverRemittance (Restrict, nullable)` (null = still in the driver's hands), `status String` CHECK (`COLLECTED`, `REMITTED`, `VERIFIED`, `DISCREPANCY`, `SETTLED`), `ledgerTransactionId → LedgerTransaction (Restrict)`.
- `@@unique([packageId])` for COD packages — a package's COD is collected exactly once; a second collection attempt is a data error the DB rejects, not a duplicate the app must dedupe.
- Indexes: `(collectedByDriverId, status)`, `(remittanceId)`.

### DriverRemittance
A rider handing cash/evidence to the company (spec §13.4 steps 7–9).
- `driverId → Driver (Restrict)`, `submittedAt`, `declaredAmountPaisa BigInt` (what the rider says they are handing over), `countedAmountPaisa BigInt?` (what Finance actually counted), `discrepancyPaisa BigInt?` — **stored as counted − declared at verification time**, never silently zeroed.
- `status String` CHECK (`SUBMITTED`, `UNDER_VERIFICATION`, `VERIFIED`, `DISCREPANCY`, `CLOSED`), `verifiedById → User (Restrict, nullable)`, `verifiedAt`, `evidenceFileId → FileAsset (Restrict, nullable)`, `notes String?`.
- Invariant: if `discrepancyPaisa ≠ 0`, the service opens a finance `Incident` (`COD_DISCREPANCY`) and the short amount is **excluded from vendor settlement** until the incident resolves (Scenario 5). Collections join a remittance via `CODCollection.remittanceId`; Σ collections in a remittance must equal the remittance's declared amount or the difference is itself the discrepancy.

### VendorSettlement
Periodic payable settlement to a vendor (spec §13.4 steps 10–13). Successor to legacy `settlements`, which had no line items and could not be traced to individual collections (audit §1.5).
- `vendorId → Vendor (Restrict)`, `periodStart`/`periodEnd Date`, `grossCodPaisa BigInt`, `shippingChargesPaisa BigInt`, `otherDeductionsPaisa BigInt`, `netPayablePaisa BigInt` (= gross − charges − deductions, computed by the service and stored as the *approved* figure at approval time).
- `status String` CHECK (`PENDING`, `RECONCILED`, `APPROVED`, `SETTLED`, `DISPUTED`, `CANCELLED`) — superset of the legacy `cod_settlement_status` flow.
- `approvedById → User (Restrict, nullable)` (requires `settlement.approve`), `settledAt`, `paymentRef String?`, `statementFileId → FileAsset (Restrict, nullable)`.

### VendorSettlementLine
Traceability, one row per settled obligation. `settlementId → VendorSettlement (Restrict)`, `codCollectionId → CODCollection (Restrict, nullable)`, `invoiceId → Invoice (Restrict, nullable)`, `kind String` (`COD_CREDIT`, `SHIPPING_CHARGE`, `DEDUCTION`, `ADJUSTMENT`), `amountPaisa BigInt`. A `CODCollection` may appear on **at most one** settlement line (unique index on `codCollectionId` where not null) — double-settlement is a DB error, not a report discrepancy.

### Refund
`paymentId → Payment (Restrict)`, `amountPaisa BigInt`, `reason String`, `status String` (`REQUESTED`, `APPROVED`, `PROCESSED`, `REJECTED`), `requestedById → User (Restrict)`, `approvedById → User (Restrict, nullable)`, `processedAt`, `ledgerTransactionId → LedgerTransaction (Restrict, nullable)`. A processed refund posts a reversing ledger entry; the original Payment row keeps its history and gains only a status change.

### FinancialAdjustment
The only legal way to change a financial outcome after the fact (spec §4.9). `targetType String` (`PAYMENT`, `INVOICE`, `COD_COLLECTION`, `SETTLEMENT`, `LEDGER`), `targetId String` (UUID of the target row), `amountPaisa BigInt`, `reason String` (mandatory), `status String` (`REQUESTED`, `APPROVED`, `REJECTED`, `APPLIED`), `createdById → User (Restrict)`, `approvedById → User (Restrict, nullable)` (four-eyes: approver ≠ creator, service-enforced for amounts above a `SystemSetting` threshold), `ledgerTransactionId → LedgerTransaction (Restrict, nullable)` — applying an adjustment *creates* the ledger entry; it never edits the target's amounts.

## 10. Operations

### Task
Work management (spec Part 15) — distinct from `DeliveryAssignment`, which is operational package work. (Legacy had no such table; `driver_tasks` was misread as one, audit §5.)
- `title String`, `description String?`, `createdById → User (Restrict)`, `assigneeId → User (Restrict)`, `warehouseId → Warehouse (Restrict, nullable)`.
- `priority String` CHECK (`LOW`, `NORMAL`, `HIGH`, `URGENT`), `status String` CHECK (`DRAFT`, `ASSIGNED`, `ACCEPTED`, `IN_PROGRESS`, `BLOCKED`, `SUBMITTED`, `UNDER_REVIEW`, `VERIFIED`, `CLOSED`, `REJECTED`, `CANCELLED`) — spec §15.2.
- `dueAt DateTime?`, `relatedPackageId → Package (Restrict)`, `relatedShipmentId → Shipment (Restrict)`, `relatedTransferId → Transfer (Restrict)`, `relatedIncidentId → Incident (Restrict)` — all nullable.
- Accountability timestamps: `acceptedAt`, `submittedAt`, `verifiedAt`, `closedAt`; `reassignmentReason String?` + previous assignee preserved via `AuditLog`/task comments (spec §15.3).
- Indexes: `(assigneeId, status, dueAt)`, `(warehouseId, status)`, `(status, dueAt)` (overdue scans).

### TaskComment
`taskId → Task (Restrict)`, `authorId → User (Restrict)`, `body String`, `createdAt`. Attachments are `FileAsset`s with `entityType = TASK`. Append-only in practice (comments are not edited; corrections are new comments).

### Incident
The exceptions/incidents register (spec Part 16).
- `incidentNumber String @unique`, `category String` CHECK — the §16.1 set: `MISSING_PACKAGE`, `DAMAGED_PACKAGE`, `WRONG_WAREHOUSE`, `WRONG_PACKAGE_RECEIVED`, `TRANSFER_SHORTAGE`, `TRANSFER_EXCESS`, `DELIVERY_FAILURE`, `CUSTOMER_REFUSAL`, `INCORRECT_ADDRESS`, `PICKUP_FAILURE`, `DRIVER_BREAKDOWN`, `VEHICLE_ACCIDENT`, `THEFT_SUSPICION`, `COD_DISCREPANCY`, `PAYMENT_DISPUTE`, `DUPLICATE_BOOKING`, `DUPLICATE_SCAN`, `WEIGHT_DISCREPANCY`, `DELAYED_SHIPMENT`, `CUSTOMER_COMPLAINT`, `UNAUTHORISED_ACCESS_ATTEMPT`, `HANDOVER_DISCREPANCY`.
- `severity String` CHECK (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), `status String` CHECK (`REPORTED`, `ACKNOWLEDGED`, `ASSIGNED`, `INVESTIGATING`, `AWAITING_INFORMATION`, `ESCALATED`, `RESOLUTION_PROPOSED`, `RESOLUTION_APPROVED`, `RESOLVED`, `CLOSED`) — spec §16.3.
- Links (nullable, Restrict): `packageId`, `orderId`, `transferId`, `tripId`, `warehouseId`, `codCollectionId`, `remittanceId`.
- `reporterId → User (Restrict)`, `assigneeId → User (Restrict, nullable)`, `responsibleTeam String?`, `description String`, `investigationNotes String?`, `resolution String?`, `resolutionApprovedById → User (Restrict, nullable)`, `createdAt`, `resolvedAt`, `closedAt`.
- Invariant (spec §16.3): a package under a `MISSING_PACKAGE` incident stays in inventory/custody records as a discrepancy — the incident workflow, not a delete, is how it leaves the books, and only an approved resolution can write it off (with a `FinancialAdjustment`/inventory `CORRECTION` movement recording the outcome).
- Indexes: `(status, severity)`, `(packageId)`, `(warehouseId, status)`, `(assigneeId, status)`.

### IncidentEvidence
Join between Incident and FileAsset with context: `incidentId → Incident (Restrict)`, `fileId → FileAsset (Restrict)`, `uploadedById → User (Restrict)`, `caption String?`, `createdAt`. `@@unique([incidentId, fileId])`.

### Approval
Generic four-eyes record for sensitive actions (spec §4.1, §21): delivery-without-proof, financial adjustments above threshold, transfer write-offs, settlement approval.
- `kind String`, `entityType String`, `entityId String`, `requestedById → User (Restrict)`, `decidedById → User (Restrict, nullable)`, `status String` (`PENDING`, `APPROVED`, `REJECTED`), `reason String`, `decisionNote String?`, `createdAt`, `decidedAt`. DB CHECK: `decidedById ≠ requestedById` when both set.

### Notification
Per-user, event-linked (spec Part 17) — replaces the legacy global-only `admin_notifications`/`admin_messages`.
- `userId → User (Restrict)`, `category String` (mirrors the Part 17 category lists: `NEW_BOOKING`, `TRANSFER_DISCREPANCY`, `MISSING_PACKAGE`, `COD_DISCREPANCY`, `OUT_FOR_DELIVERY`, `DELIVERED`, …), `title String`, `body String`.
- `entityType String?`, `entityId String?` (deep-link target), `dedupeKey String? @unique` — retries of the originating event regenerate the same key and collide instead of double-notifying (spec Part 17).
- `readAt DateTime?`, `createdAt`. Indexes: `(userId, readAt, createdAt)`.

### NotificationPreference
`userId → User (Cascade — configuration)`, `category String`, `channel String` (`IN_APP`, `EMAIL`, `SMS`), `enabled Boolean`. `@@unique([userId, category, channel])`. In-app is always available; EMAIL/SMS rows only take effect when the respective provider keys exist (they are blank in the current environment — in-app ships first, per spec).

### AuditLog — append-only
The general-purpose trail the legacy system lacked entirely (audit §5, R9): user/role changes, settings changes, financial actions, denied access.
- `actorId → User (Restrict, nullable)` (null for anonymous/denied attempts), `actorRole String?`, `action String` (e.g. `user.suspend`, `role.assign`, `settings.update`, `finance.adjust`, `auth.login_failed`, `authz.denied`).
- `entityType String`, `entityId String?`, `warehouseId → Warehouse (Restrict, nullable)` (scope of the action), `before Json?`, `after Json?` (diffs, with secrets/PII redacted by the writer), `ipAddress String?`, `userAgent String?`, `createdAt`.
- Indexes: `(entityType, entityId)`, `(actorId, createdAt)`, `(action, createdAt)`. No update/delete path; protected by the append-only trigger like other history tables.

## 11. Platform

### FileAsset
Every uploaded file (POD photos, signatures, driver documents, vendor verification documents, incident evidence, label PDFs). Files live in **private** object storage (Cloudinary private / Supabase Storage private bucket); the DB stores metadata only.
- `storageKey String @unique`, `bucket String`, `originalName String`, `mimeType String` (server-verified, not the browser's claim — spec §21.4), `sizeBytes Int`, `sha256 String` (integrity + dedupe).
- `entityType String`, `entityId String` (polymorphic owner: `PACKAGE`, `DRIVER`, `VENDOR`, `INCIDENT`, `TASK`, `USER`…) — deliberately *not* an FK: assets attach to many aggregates, and integrity is enforced by the upload service, which only creates an asset in the same request that authorises it against a real entity. Typed nullable FKs on the owning tables (`ProofOfDelivery.photoFileId`, `Driver.profilePhotoFileId`, …) provide the navigable direction.
- `uploadedById → User (Restrict)`, `visibility String @default("PRIVATE")`, `createdAt`. Downloads are always via short-lived signed URLs minted after an authorisation check; no public paths for sensitive documents.

### SystemSetting
Successor to legacy `admin_settings` (which held `auto_assign`, `realtime_tracking`, `customer_alerts`). `key String @unique`, `value Json`, `description String?`, `updatedById → User (Restrict)`, `updatedAt`. Holds, among others: volumetric divisor (spec §6.3), MFA-required roles, adjustment approval threshold, GPS retention days, delivery-proof requirements per service, notification provider toggles.

### ServiceArea
A deliverable geography. `name String`, `district String`, `city String?`, `province String`, `servingWarehouseId → Warehouse (Restrict)` (the warehouse that delivers here), `isActive Boolean`. `@@unique([district, name])`. Indexes: `(district)`, `(servingWarehouseId)`. Routing and rider batching group by ServiceArea (spec §11.2).

### PricingRule
Tariff configuration — prices are data, never code (spec §6.3).
- `shippingServiceId → ShippingService (Restrict)`, `originServiceAreaId → ServiceArea (Restrict, nullable)`, `destinationServiceAreaId → ServiceArea (Restrict, nullable)` (null = any), `minWeightKg`/`maxWeightKg Decimal?` bands.
- `baseRatePaisa BigInt`, `perKgRatePaisa BigInt`, `codFeePercent Decimal?`, `volumetricDivisor Int` (e.g. 5000 — the §6.3 formula divisor is per-rule configuration, not a constant).
- `effectiveFrom DateTime`, `effectiveTo DateTime?`, `isActive Boolean`, `createdById → User (Restrict)`. Rule resolution: most specific active rule for (service, origin, destination, billable weight) at booking time; the result is snapshotted onto the Shipment.

### ShippingService
`code String @unique` (`STANDARD`, `EXPRESS`, `SAME_DAY`), `name String`, `estimatedDaysMin/Max Int?`, `requiresProofMethod String?` (default POD method for the service), `isActive Boolean`.

### JobRecord
Durable background-job ledger (spec Part 20 platform list) — daily reports, GPS retention, notification fan-out, settlement statement generation. Replaces the legacy GitHub-Actions cron + `cleanup_gps_tracking()` arrangement.
- `jobType String`, `status String` (`PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED`), `payload Json?`, `result Json?`, `attempts Int @default(0)`, `lastError String?`, `scheduledAt`, `startedAt?`, `finishedAt?`, `idempotencyKey String? @unique`. Index: `(status, scheduledAt)`.

## 13. Migration approach

1. **Backup first, always.** Full `pg_dump` (schema + data) of the live Supabase project, plus a separate dump of `auth.users` metadata (ids/emails only) for identity reconciliation. Verify the dump by restoring it into a scratch database before anything else happens. No migration step runs against live data without this backup existing (spec §2.5, Part 30 rule 21; audit R1 — the live DB is *not* reproducible from the repo: 3 tables and ~31 columns exist only live).
2. **Provision alongside, never in place.** Prisma creates the new schema in a dedicated `app` PostgreSQL schema in the same database. The legacy `public` schema stays fully intact and the old system keeps running until cut-over is verified; afterwards `public` is renamed/archived as legacy, not dropped, until the owner signs off.
3. **Master data migrates; demo transactional data does not.** Migrated: 4 warehouses (with district backfill), 9 user accounts (reconciled against `auth.users` per audit R4 — any `public.users` row without an Auth counterpart is flagged to the owner before migration, since it cannot log in), 4 drivers (+ capabilities), 4 vehicles, 5 warehouse memberships, 1 customer, 3 system settings. **Not migrated:** the 2 demo parcels (`BLA-DEMO-0001/0002`), the demo trip/manifest/task, all 13 `dev-bypass` shipment events, GPS pings, the Acme demo vendor (IN residue, audit R10), the zero-amount settlement placeholder, admin seed content, and the 7 app-created inventory intake rows (audit §2.1 marks these ambiguous — excluded by default; the owner can override for specific rows before cut-over, since they were created through the product, not a seed script). There is no real order/payment/COD history to lose: those tables are empty (audit §2).
4. **Identity cut-over.** Migrated users get `User` rows with roles/memberships and a `UserInvitation` (password-set) flow — Supabase Auth hashes cannot be extracted, so first login on the new system is a password set/reset, communicated to the 2 real-shaped accounts directly. The new `User` keeps the legacy UUID as its `id` wherever the account is confirmed real, preserving every FK relationship in migrated master data.
5. **Phase 3c district gap — resolved in the new model.** `Warehouse.district` is a required column (not the optional afterthought that never reached production), `ServiceArea` carries district, and orders/shipments snapshot `destinationDistrict`. The district-based routing rule (same district → `LAST_MILE`, different → `INTER_WAREHOUSE`) reads these first-class fields. Backfill for the 4 warehouses: Kathmandu (WH-KTM-01), Kaski (WH-PKR-01, Pokhara), Chitwan (WH-CHT-01, Bharatpur), Lalitpur (WH-LTP-01) — to be confirmed against the warehouse addresses during the migration run.
6. **Verification gates.** Row-count and checksum comparison for every migrated master-data table; a login + role + membership smoke test per migrated user class; warehouse-isolation tests (Warehouse A credentials cannot read Warehouse B inventory — spec §26.3) run against the migrated data before the old backend is retired (audit R2: the old backend *is* the current authorisation layer, so it is the last thing switched off, not the first).
